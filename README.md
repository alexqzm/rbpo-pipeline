# rbpo-pipeline

[![CI](https://github.com/alexqzm/rbpo-pipeline/actions/workflows/ci.yml/badge.svg)](https://github.com/alexqzm/rbpo-pipeline/actions/workflows/ci.yml)
[![Самопроверка](https://github.com/alexqzm/rbpo-pipeline/actions/workflows/selftest.yml/badge.svg)](https://github.com/alexqzm/rbpo-pipeline/actions/workflows/selftest.yml)

Конвейер GitHub Actions, который на каждом запуске собирает технические артефакты ГОСТ Р 56939-2024
«Разработка безопасного программного обеспечения»: отчёт статического анализа с разметкой
срабатываний, перечень зависимостей и известные уязвимости, антивирусную проверку заимствованного
кода, отчёт и журнал тестирования, журнал сборки, подтверждение хранения и повторяемости сборки,
аттестации происхождения и их проверку, анализ неустранённых ошибок. Из них и из организационных
документов проекта конвейер строит манифест для [`rbpo-evidence`](https://github.com/alexqzm/rbpo-evidence),
получает отчёт о полноте свидетельств по всем 25 процессам стандарта и принимает решение по выпуску.

> **Это не оценка соответствия и не текст стандарта.** Конвейер формирует свидетельства и проверяет
> их полноту; методику оценки соответствия стандарт относит к отдельному национальному стандарту
> (п. 4.4). Номера и краткие наименования артефактов взяты из модели `rbpo-evidence`, формулировки
> там — пересказы, а не текст стандарта. Содержание регламентов и других организационных документов
> конвейер не оценивает: он проверяет, что документ есть, и кладёт его копию в комплект.

## Что формирует конвейер

У каждого артефакта три состояния, как в методе SCII: **P** — предъявлен и подтверждает, **F** —
предъявлен и опровергает, **N** — не предъявлен.

| Артефакт | Что формирует конвейер | F, если |
|---|---|---|
| 5.4.3.3 контроль изменений ПО и документации | коммиты и изменённые файлы диапазона (ПО и документация отдельно) | — |
| 5.10.3.2 перечень инструментов SAST | инструменты, версии, языки проекта и их покрытие анализом | у языка проекта нет анализа и нет обоснования |
| 5.10.3.3 конфигурации SAST | набор правил с уровнями и хэшем, порог, решения разметки | — |
| 5.10.3.4 отчёты SAST с разметкой | SARIF Semgrep; решения из файла разметки записаны в SARIF как подавления с обоснованием | срабатывание не ниже порога без решения или подтверждённое |
| 5.12.3.2 сведения о сборочной среде | ОС и образ исполнителя, Python, закреплённые и фактические версии инструментов | версия инструмента не совпала с закреплённой |
| 5.13.3.4 журналы аудита сборки | журнал сборки, команда, время, код, SHA-256 журнала и результатов | — |
| 5.13.3.5 подтверждение хранения результатов | результаты, загруженные из хранилища артефактов, сверены с контрольными суммами сборки | не совпали |
| 5.13.3.6 подтверждение повторяемости | вторая сборка на другом исполнителе, сравнение побитово | результаты различаются |
| 5.14.3.3 контроль целостности кода | дерево сборки совпадает с коммитом, хэш дерева и архива, подписи коммитов (GitHub API) | дерево изменено; подпись недействительна; нет подписи при `commit_signatures: require` |
| 5.16.3.2 перечень зависимостей | SBOM CycloneDX (Syft): компоненты, версии, источник (purl) | — |
| 5.16.3.4 анализ заимствованных компонентов | известные уязвимости и их критичность (Grype) непосредственно перед сборкой | уязвимость не ниже порога без решения или подтверждённая |
| 5.17.3.5 антивирусная проверка | ClamAV: каталог проекта и установленные пакеты Python | найдено заражение |
| 5.18.3.2 отчёт о функциональном тестировании | JUnit: тесты, отказы, пропуски | тест не прошёл |
| 5.18.3.3 журналы функционального тестирования | JUnit (время и результат каждого теста) и вывод запуска | — |
| 5.20.3.2 анализ влияния неустранённых ошибок | все неустранённые срабатывания, уязвимости и отказы тестов с решениями по ним | есть ошибка выше порога без решения |
| 5.20.3.4 проверка мер обеспечения целостности | `gh attestation verify` для каждого результата сборки | аттестация не подтверждена |

Подробные правила — в [`docs/artifacts.md`](docs/artifacts.md). Организационные артефакты
(регламенты, перечни, схемы) проект указывает в `rbpo.yaml`; пример — руководство демонстрационного
проекта [`examples/demo-app/docs/rbpo-guide.md`](examples/demo-app/docs/rbpo-guide.md), где в одном
документе собраны 15 таких артефактов.

## Подключение

В репозитории проекта — рабочий процесс, который вызывает конвейер. Закрепите и рабочий процесс,
и устанавливаемый пакет одним и тем же коммитом rbpo-pipeline:

```yaml
name: РБПО
on:
  push:
    branches: [main]
    tags: ["v*"]
  pull_request:

permissions: {}

jobs:
  rbpo:
    uses: alexqzm/rbpo-pipeline/.github/workflows/rbpo.yml@<коммит>
    permissions:
      contents: read
      id-token: write       # аттестации происхождения (Sigstore)
      attestations: write
    with:
      pipeline-spec: git+https://github.com/alexqzm/rbpo-pipeline@<коммит>
      install-command: python -m pip install -e ".[test]"
      test-command: python -m pytest --junitxml="$RBPO_JUNIT"
```

Параметры (`with:`):

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `working-directory` | `.` | каталог проекта в репозитории |
| `python-version` | `3.13` | Python для установки, тестов и сборки |
| `install-command` | — | установка проекта и зависимостей тестов |
| `test-command` | — | тесты; отчёт JUnit — в файл `$RBPO_JUNIT` |
| `build-command` | `python -m build` (build 1.6.1) | сборка; результаты — в `dist-dir` |
| `dist-dir` | `dist` | каталог результатов сборки |
| `config` | `rbpo.yaml` | настройки конвейера |
| `semgrep-config` | `p/default` | набор правил Semgrep |
| `attest` | `true` | аттестации результатов сборки и комплекта (кроме запросов на слияние) |
| `pipeline-repository` | `alexqzm/rbpo-pipeline` | репозиторий конвейера: подписант аттестаций |
| `pipeline-spec` | ветка `main` | требование pip для установки rbpo-pipeline |

Выходы: `decision` (`pass` или `fail`) и `overall` (итог rbpo-evidence: `confirmed`, `missing`,
`refuted`).

### Настройки проекта — `rbpo.yaml`

```yaml
project: "Мой проект"
policy:
  sast_fail_on: error          # error | warning | note | none
  sca_fail_on: critical        # critical | high | medium | low | none
  secrets: fail                # fail | report — найденный секрет останавливает выпуск
  commit_signatures: report    # report | require — коммит без проверенной подписи опровергает 5.14.3.3
  reproducible: require        # require | report — различие сборок останавливает выпуск
triage: .rbpo/triage.yaml
sast_exclude_languages:        # язык без статического анализа — только с обоснованием
  Bash: "служебные скрипты CI, в поставку не входят"
scope:
  exclude:                     # процессы вне области применения — с обоснованием
    - {process: "5.25", reason: "вывод из эксплуатации вне договора"}
organizational:                # документ (можно с якорем раздела) для организационного артефакта
  "5.10.3.1": docs/rbpo-guide.md#статический-анализ
```

### Решения по срабатываниям и уязвимостям — `.rbpo/triage.yaml`

```yaml
sast:
  - rule: "python.lang.security.audit.subprocess-shell-true.*"   # шаблоны правила и пути
    path: "src/tool/run.py"
    verdict: false_positive    # false_positive | accepted | confirmed
    reason: "команда собирается из констант"
vulnerabilities:
  - id: CVE-2020-14343         # или GHSA; сравнивается и со связанными идентификаторами
    package: pyyaml
    verdict: not_affected      # not_affected | accepted | confirmed
    reason: "FullLoader в проекте не используется"
    until: 2027-03-01          # после даты решение не действует
```

`false_positive` и `not_affected` — срабатывание ложное, уязвимость недостижима; `accepted` —
ошибка признана и оставлена в выпуске с обоснованием (это и есть анализ влияния для 5.20.3.2);
`confirmed` — признана и подлежит исправлению, выпуск с ней не допускается.

## Результат запуска

- **Сводка** в итогах запуска (job summary): решение по выпуску, состояния всех артефактов,
  полнота по 25 процессам.
- **Артефакт `rbpo-evidence`**: архив комплекта свидетельств, `report.md` (отчёт rbpo-evidence),
  `manifest.yaml`, `SUMMARY.md`. Архив подписан аттестацией происхождения.

Состав комплекта:

```
states/<артефакт>.json   состояние, файлы, числа, пояснение — по каждому артефакту
source/                  changes.json, integrity.json
sast/  sca/  secrets/  av/  tests/  env/
build/  rebuild/         журналы, сведения о сборке, SHA256SUMS
verify/                  storage.json, repro.json, attestations.json
org/                     organizational.json и копии документов
release/unresolved.json  неустранённые ошибки и решения по ним
manifest.yaml  report.md  report.json  SUMMARY.md  decision.json
index.json               SHA-256 каждого файла комплекта
```

Хранение артефактов рабочего процесса ограничено настройками репозитория (обычно 90 дней): для
выпусков приложите архив комплекта к выпуску GitHub.

## Решение по выпуску

Выпуск не допускается (задача `report` завершается с ошибкой), если:

- хотя бы один технический артефакт в состоянии F (различие сборок — только при
  `reproducible: require`);
- шаг не дал свидетельства из-за сбоя инструмента;
- найден секрет или поиск секретов не выполнен (при `secrets: fail`);
- сборка завершилась с ошибкой или задача конвейера не выполнена.

Непредъявленные организационные артефакты выпуск не останавливают: они видны в отчёте о
полноте как недостающие. Решение учитывает свидетельства сборочной среды и целостности кода
(5.13, 5.14), хотя анализ при выпуске (5.20.2.2) в стандарте на них не ссылается.

## Как устроен конвейер

```
analyze ─┬─ build ───┬─ verify ── report
         └─ rebuild ─┘
```

| Задача | Что делает | Права токена |
|---|---|---|
| analyze | изменения и целостность кода, секреты, SAST, SBOM и уязвимости, документы, тесты, антивирус, среда | чтение кода |
| build | сборка с журналом, хранилище, аттестация результатов | чтение кода, OIDC, запись аттестаций |
| rebuild | независимая повторная сборка на другом исполнителе | чтение кода |
| verify | сверка из хранилища, сравнение сборок, проверка аттестаций | чтение кода и аттестаций |
| report | анализ неустранённых ошибок, манифест, отчёт rbpo-evidence, опись, аттестация комплекта, решение | чтение кода, OIDC, запись аттестаций |

Сам конвейер следует тем же правилам: все действия закреплены полным SHA коммита, архивы Syft,
Grype и Gitleaks проверяются по SHA-256 ([`rbpo_pipeline/tools.json`](rbpo_pipeline/tools.json)),
новые версии инструментов берутся не раньше чем через 14 дней после выпуска, учётные данные при
получении кода не сохраняются, права токена заданы для каждой задачи.

Шаги можно запускать и вне GitHub Actions: `rbpo-pipeline <шаг> --out <каталог>`
(`rbpo-pipeline --help`).

## Работа с ИИ-агентом

Разбор срабатываний и уязвимостей можно поручить ИИ-агенту, но файл разметки он не правит: запись
в `.rbpo/triage.yaml` снимает блокировку выпуска. Агент пишет предложения в `.rbpo/proposals/`,
конвейер этот каталог не читает, решение в файл разметки переносит человек.

```sh
rbpo-pipeline triage-queue --out .rbpo-evidence                           # что ждёт решения
rbpo-pipeline proposals-check --out .rbpo-evidence .rbpo/proposals/*.yaml  # проверка предложений агента
rbpo-pipeline agent-guard --base origin/main                              # ветка агента меняет только предложения
```

`proposals-check` отклоняет предложения с шаблонами, принятием риска, решениями без срока
пересмотра и ссылками на код, которые дословно не совпадают с файлами проекта. Она подтверждает
форму предложения и существование процитированных строк, а не правильность вывода.

Описание по порядку со схемами — в [`agent/README.md`](agent/README.md): из чего состоит агент и
что такое обвязка агента, как идёт работа, разбор одного элемента от очереди до решения, требования
к обвязке, испытания на стенде. Там же правила для агента, скилл, журнал ошибок, программа
испытаний и стенд с известными ответами. Справочник по командам, правилам проверки и угрозам —
в [`docs/agent.md`](docs/agent.md).

## Ограничения

- Исполнители Linux x64; сборка по умолчанию — Python (`python -m build`), для других языков
  задайте `build-command`, `install-command` и `test-command`.
- Перечень зависимостей строится по файлам проекта (`requirements.txt`, файлы блокировок),
  а не по установленному окружению.
- База ClamAV обновляется при запуске (`freshclam`); если обновление не удалось, используется база
  образа, её версия и дата записываются в свидетельство.
- Аттестации доступны в публичных репозиториях и в GitHub Enterprise Cloud; для запросов на
  слияние они не создаются, артефакт 5.20.3.4 тогда не предъявлен.
- Правила Semgrep из реестра и база Grype загружаются из сети при каждом запуске.

### Summary (EN)

A reusable GitHub Actions workflow that produces the technical artifacts of the Russian secure
software development standard GOST R 56939-2024 on every run — SAST report with triage (SARIF
suppressions), CycloneDX SBOM and known-vulnerability analysis, antivirus scan of third-party
code, test report and log, build audit log, storage and bit-for-bit reproducibility checks, build
provenance attestations and their verification, and an analysis of unresolved defects — then
builds an `rbpo-evidence` manifest, evaluates evidence completeness across all 25 processes of the
standard (three-valued: supports, refutes, not presented) and makes a release decision. This is an
evidence-completeness check, not a conformity assessment. An optional kit lets an AI agent propose
triage decisions without being able to make them: proposals live outside the triage file, are
checked for exact code quotations and scope, and a human transfers the accepted ones.

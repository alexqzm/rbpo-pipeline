# Работа с ИИ-агентом: предложения по разметке

Срабатывание статического анализа или уязвимость зависимости выше порога останавливают выпуск,
пока в файле разметки `.rbpo/triage.yaml` нет решения. Разбор таких элементов — повторяемая работа,
и её можно поручить ИИ-агенту: найти, как пакет используется в коде, проследить, откуда берётся
опасное значение, подготовить обоснование.

Но файл разметки — это управляющий элемент конвейера: запись `not_affected` или `false_positive`
снимает блокировку выпуска. Агент, который может менять разметку, может сделать конвейер «зелёным»,
не устранив ни одной ошибки. Поэтому работа разделена: агент пишет **предложения** в отдельный
каталог `.rbpo/proposals/`, которого конвейер не читает; **решение** в файл разметки переносит
человек. Между ними стоят две проверки, которые не зависят от послушания модели.

Готовые правила для агента, скилл, журнал ошибок, программа испытаний и стенд лежат в каталоге
[`agent/`](../agent/README.md).

## Кто что делает

| Участник | Что делает | Чего не делает |
|---|---|---|
| Конвейер | собирает комплект свидетельств, применяет решения из `.rbpo/triage.yaml`, принимает решение по выпуску | не читает каталог предложений |
| Агент | читает очередь разметки и код, пишет предложения с дословными цитатами из кода | не меняет разметку, настройки и код; не запускает код; не предлагает принять риск |
| `rbpo-pipeline proposals-check` | отклоняет предложения, нарушающие правила ПП01–ПП11; пишет отчёт для человека | не оценивает, верен ли вывод агента |
| `rbpo-pipeline agent-guard` | отклоняет ветку агента с изменениями вне каталога предложений | не проверяет содержание предложений |
| Человек | читает предложения, сам убеждается в выводе, переносит решение в файл разметки, ведёт журнал ошибок | — |

## Команды

```sh
rbpo-pipeline triage-queue --out .rbpo-evidence --json .rbpo/proposals/queue.json
rbpo-pipeline proposals-check --out .rbpo-evidence --md отчёт.md .rbpo/proposals/2026-11-16-1.yaml
rbpo-pipeline agent-guard --base origin/main
```

**`triage-queue`** читает `sca/triage.json` и `sast/triage.json` комплекта и показывает, что ждёт
решения: элементы, которые блокируют выпуск, элементы ниже порога и подтверждённые к исправлению.
Элементы с действующим решением в очередь не входят. О найденных секретах команда сообщает только
число: в разметку они не входят и агенту не передаются.

**`proposals-check`** проверяет файлы предложений по комплекту свидетельств и файлам проекта.
Ключи: `--max-days` — наибольший срок пересмотра (по умолчанию 180 дней), `--date` — дата проверки,
`--json` и `--md` — результат для программы и отчёт для человека. В отчёте Markdown предложения,
прошедшие проверку, приведены в формате файла разметки, чтобы человек мог перенести принятые.
Коды возврата: 0 — нарушений нет, 1 — есть, 2 — ошибка входных данных.

**`agent-guard`** сравнивает ветку с точкой её ответвления от `--base` и отклоняет любое изменение
вне `.rbpo/proposals/*.yaml`, `*.yml`, `*.md`, `*.json`. В разрешённых путях файлы можно только
добавлять и менять; удаление, символическая ссылка и исполняемый файл отклоняются. Ключ `--allow`
заменяет разрешённые шаблоны, пути задаются относительно каталога проекта.

## Файл предложений

Образец с пояснениями —
[`agent/skills/rbpo-triage/assets/proposals.example.yaml`](../agent/skills/rbpo-triage/assets/proposals.example.yaml).

```yaml
schema: rbpo-pipeline/triage-proposals/v1
meta:
  agent: "оболочка агента и версия"
  model: "модель и версия"
proposals:
  - kind: vulnerability            # vulnerability | sast
    id: GHSA-8q59-q68h-6hv4        # как в очереди; подходит и связанный идентификатор CVE
    package: pyyaml                # точное имя
    version: "5.3"                 # в кавычках, как в очереди
    verdict: not_affected          # not_affected | confirmed; для sast: false_positive | confirmed
    reason: "Уязвимы full_load и FullLoader; проект читает YAML только через safe_load."
    until: 2027-02-01              # срок пересмотра снимающего решения
    refs:                          # ссылки на код проекта с дословной цитатой
      - path: src/config.py
        line: 7
        quote: "return yaml.safe_load(fh)"
```

Для срабатывания статического анализа вместо `id`, `package`, `version` указываются `rule`, `path`
и `line`. Файл считается недоверенным: его написала модель, которая могла прочитать чужой текст.
Поэтому неизвестные и повторяющиеся ключи, управляющие и невидимые символы, файл больше 1 МиБ и
больше 500 предложений в файле отклоняются.

## Правила проверки

| Код | Правило | Что отсекает |
|---|---|---|
| ПП01 | формат файла предложений | файл, который человек и программа прочли бы по-разному: повтор ключа, лишние поля, невидимые символы, версия числом |
| ПП02 | предложение не относится ни к одному элементу комплекта свидетельств | решение по срабатыванию или уязвимости, которых нет |
| ПП03 | шаблон вместо точного значения | решение, которое снимает больше, чем разобрано: `package: "*"`, `rule: "python.*"` |
| ПП04 | принятие риска (accepted) агент не предлагает | перенос решения владельца риска на модель |
| ПП05 | обоснование слишком короткое | решение без объяснения |
| ПП06 | снимающее решение без ссылки на код проекта | `not_affected` и `false_positive` без опоры на код |
| ПП07 | ссылка на код не подтверждается | выдуманные файлы, строки и цитаты; ссылки за пределы проекта, на служебные каталоги и на комплект свидетельств |
| ПП08 | срок пересмотра не задан или вне допустимого | бессрочное снятие |
| ПП09 | повторное предложение по тому же элементу | противоречивые предложения |
| ПП10 | версия пакета в предложении не та, что в комплекте свидетельств | предложение, подготовленное по устаревшей очереди |
| ПП11 | по элементу уже есть решение в файле разметки | пересмотр решения человека |

Ссылка на код (ПП07) проверяется дословно: цитата после приведения пробелов должна входить в текст
указанных строк файла, быть не короче 8 знаков без пробелов и не длиннее 20 строк. Путь
приводится к каноническому виду; символическая ссылка за пределы проекта отклоняется.

Проверка дополнительно предупреждает, если предложено снять все блокирующие элементы и если
комплект свидетельств получен для другого коммита.

**Чего проверка не видит.** Она подтверждает, что предложение оформлено по правилам и что
процитированные строки существуют. Следует ли вывод из этих строк, она не знает: настоящая цитата
при неверном выводе проверку проходит. На стенде это исход «опасно», и ловит его только человек
или эталон.

## Угрозы и меры

Классы угроз — по [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications/).

| Угроза | Как проявляется здесь | Мера |
|---|---|---|
| ASI01 Agent Goal Hijack | в описании уязвимости, комментарии или README записана инструкция агенту: снять уязвимость, изменить порог | данные не считаются поручениями (правила, скилл); агент не может сам записать решение (`agent-guard`); снятие требует цитаты и срока (ПП06–ПП08); ловушки Л1 и Л2 стенда |
| ASI02 Tool Misuse & Exploitation | агент запускает код проекта, тесты, установку пакетов, обращается к сети | запрет в правилах; ограничение средствами оболочки агента (вне набора); журнал вызовов в испытаниях |
| ASI03 Identity & Privilege Abuse | у агента есть право записи в основную ветку или в файл разметки | отдельная учётная запись с правом отправки только в ветки `agent/**`; обязательная проверка `agent-guard`; `CODEOWNERS` для разметки и настроек |
| ASI04 Agentic Supply Chain Vulnerabilities | подменены скилл, правила или сам инструмент проверки | набор и rbpo-pipeline берутся из закреплённого коммита; комплект свидетельств — из запуска конвейера, а не из каталога агента |
| ASI09 Human-Agent Trust Exploitation | убедительное обоснование принимается без проверки | отчёт для человека формирует команда проверки, а не агент; предупреждение о снятии всех блокирующих элементов; у каждого снимающего решения проверяемые цитаты и срок пересмотра |

## Что обеспечено и чем

Текст правил модель может нарушить. Ниже — что из запретов обеспечено кодом этого репозитория, а
что остаётся настройкой оболочки агента и репозитория проекта.

| Запрет | Чем обеспечен | Где |
|---|---|---|
| Не менять разметку, настройки, код, рабочие процессы | `agent-guard` как обязательная проверка запроса на слияние | этот репозиторий и настройка защиты ветки |
| Не снимать без доказательства, не снимать бессрочно, не снимать шаблоном | `proposals-check`, правила ПП03, ПП06–ПП08 | этот репозиторий |
| Не принимать риск | `proposals-check`, правило ПП04 | этот репозиторий |
| Не пересматривать решения человека | `proposals-check`, правило ПП11 | этот репозиторий |
| Не запускать код, не выходить в сеть | песочница и список разрешённых команд оболочки агента | настройка оболочки |
| Не отправлять в основную ветку | права учётной записи агента, защита ветки | настройка репозитория |
| Не отключать собственную проверку | рабочий процесс на `pull_request_target` берётся из основной ветки | [пример рабочего процесса](../agent/workflows/agent-guard.yml) |

## Ограничения

- Проверка предложений не заменяет человека: она отсекает форму ошибки, а не неверный вывод.
- Ссылки на код проверяются по рабочему каталогу проекта. Проверяйте предложения на том же коммите,
  для которого собран комплект свидетельств; при расхождении команда предупреждает.
- Стенд мал и использует синтетические отчёты инструментов; прогоны настоящего агента на нём не
  выполнялись.
- Пример рабочего процесса проверен статически и в живом репозитории не запускался.
- Песочницы для агента в наборе нет: запрет на запуск кода и сеть обеспечивает оболочка агента.
